    OpenAPI: Den Entwurf aufschreiben

    Als Mitglied des Teams, das eine API herausgibt, möchte ich unseren Entwurf in einem maschinenlesbaren Format festhalten, damit andere Teams damit arbeiten können, ohne uns zu fragen.

    Dein Entwurf steht. Jetzt schreibst Du ihn so auf, dass ein Programm ihn lesen kann.

    Diese Übung muss nicht fertig werden. Sie ist so bemessen, dass niemand alles schafft – das ist beabsichtigt, nicht Dein Tempo. Wer drei Operationen sauber hinbekommt, hat die Übung bestanden. Alles Weitere kannst Du nach dem Kurs ergänzen; das Werkzeug läuft im Browser und kostet nichts.

    Lernziele

    Du…

    • übersetzt einen formlosen API-Entwurf in ein gültiges OpenAPI-Dokument.
    • beschreibst eine Operation vollständig: Pfad, Methode, Parameter, Request-Body, Antworten mit Statuscodes und Inhalt.
    • definierst ein Schema unter components und referenzierst es mit $ref.
    • liest die Meldungen des Editors und behebst die Fehler selbst.

    Definition of Done

    • Dein Dokument hat einen gültigen Kopf: openapi, info mit title und version.
    • Mindestens drei Operationen sind vollständig beschrieben – mit allen Antworten, die Du notiert hast, nicht nur dem Erfolgsfall.
    • Mindestens ein Schema steht unter components und wird per $ref referenziert.
    • Der Editor zeigt keine Fehler mehr an.
    • Rechts im Editor siehst Du eine benutzbare Dokumentation Deiner API.
    • Du hast die Reflexionsfragen schriftlich beantwortet.

    Arbeitsschritte

    Leg den Kopf an

    Öffne editor.swagger.io, lösch das Beispiel und fang mit dem Nötigsten an:

    openapi: 3.1.0
info:
  title: Account Service API
  description: Verwaltung der Kundenkonten des Online-Shops
  version: 1.0.0
servers:
  - url: https://api.example.com/v1
paths: {}

    Der Editor beschwert sich jetzt nicht mehr. Das ist Dein Ausgangspunkt.

    Hinweis: version ist die Version Deiner API, nicht die von OpenAPI. Die steht ganz oben in openapi.

    Beschreib genau eine Operation – ganz

    Nimm Dir die einfachste lesende Operation vor, meist GET /customers. Und mach sie vollständig, bevor Du die nächste anfängst.

    paths:
  /customers:
    get:
      summary: Alle Kunden lesen
      responses:
        '200':
          description: Die Liste der Kunden
          content:
            application/json:
              schema:
                type: array
                items:
                  type: object
                  properties:
                    id:
                      type: string
                    name:
                      type: string

    Sieh Dir die rechte Seite an. Da steht jetzt Deine API.

    Hinweis: Die Anführungszeichen um '200' sind kein Zufall. Ohne sie liest YAML eine Zahl, gefordert ist aber ein Textschlüssel. Das ist der häufigste Stolperstein.

    Hinweis: Die Verschachtelung ist immer dieselbe: Pfad → Methode → responses → Statuscode → content → Medientyp → schema. Verläufst Du Dich, zähl die Ebenen von oben durch.

    Zieh das Schema heraus

    Das Kunden-Objekt wirst Du noch mehrfach brauchen. Definier es einmal und verweis darauf:

    components:
  schemas:
    Customer:
      type: object
      required: [name]
      properties:
        id:
          type: string
          readOnly: true
        name:
          type: string
          minLength: 3

    Und in der Operation:

                  schema:
                type: array
                items:
                  $ref: '#/components/schemas/Customer'

    Hinweis: readOnly: true ist die Antwort auf eine Frage, die Du vorhin vielleicht diskutiert hast: Die ID kommt beim Lesen mit, wird beim Anlegen aber nicht mitgeschickt. So brauchst Du dafür kein zweites Schema.

    Ergänze eine schreibende Operation

    Jetzt POST /customers. Hier kommt etwas Neues dazu: ein requestBody.

    Und die Antworten sind interessanter – denk an das, was Du notiert hast: Was kommt bei Erfolg zurück? Welcher Statuscode? Steht da ein Location-Header? Und was passiert, wenn die Daten nicht taugen?

    Hinweis: Fällt Dir auf, dass Du gar nicht entschieden hast, was bei einem Fehler zurückkommt – schreib das auf. Das ist kein Versäumnis, sondern genau der Effekt, um den es hier geht: Das Format erzwingt Entscheidungen, die man formlos umgehen kann.

    Beschreib eine Operation mit Pfadparameter

    GET /customers/{id} braucht eine Deklaration des Parameters – sonst meckert der Editor.

    Überleg dabei: Der id-Parameter wird bei GET, PUT, PATCH und DELETE gleich aussehen. Wo gehört er hin, damit Du ihn nur einmal schreibst?

    Hinweis: Es gibt zwei Stellen, an denen ein Parameter stehen kann – bei der einzelnen Operation oder beim Pfad, dann gilt er für alle Methoden darunter. Und es gibt components/parameters für die Wiederverwendung über Pfade hinweg.

    Mach den Editor still

    Geh die Meldungen von oben nach unten durch. Beheb sie, bis links nichts mehr rot ist.

    Lies dabei mit, was der Editor sagt – nicht nur, dass er etwas sagt. Die Meldungen sind nützlicher, als sie aussehen.

    Hinweis: Findest Du einen Fehler nicht, schau auf die Einrückung der Zeile darüber. In YAML ist fast jeder Fehler ein Einrückungsfehler.

    Wenn noch Zeit ist

    In dieser Reihenfolge lohnt es sich weiterzumachen:

    1. Die übrigen Operationen Deines Entwurfs.
    2. Die Fehlerantworten, die Du bisher weggelassen hast.
    3. tags, um die Operationen zu gruppieren – sieh Dir an, was rechts passiert.
    4. example-Werte bei den Feldern. Das ist die Stelle, an der Deine Dokumentation plötzlich richtig gut aussieht.
