API Security: Wer hält was auf – Gateway und Service

    API Security: Wer hält was auf – Gateway und Service

    Oben zehn Anfragen, die nicht durchkommen sollten – wähle eine und sieh, an welcher Stelle sie aufgehalten wird. Darunter die Grenzen, die eine API robust machen, und die OWASP API Security Top 10 als Karte: Ein Klick auf ein Risiko zeigt, worum es geht, und die Do’s und Don’ts am Account Service.

    Diese Seite verortet Security, sie lehrt sie nicht. Sie zeigt, wo geprüft wird und welche Entscheidungen schon im Entwurf fallen. Wie Tokens ausgestellt, signiert und geprüft werden – OAuth 2, OpenID Connect, JWT, mTLS –, ist eine eigene Spezialisierung: Weiter.

    Wer hält das auf?

    Jede Anfrage kommt zuerst am Gateway an, dann beim Service. Das Gateway setzt den Vertrag (OpenAPI) durch: Was dort an Scopes, Typen und Grenzen steht, prüft es, bevor ein Service etwas davon merkt.

    Gateway prüft grob – ohne Fachwissen, gegen den Vertrag

    • Token prüfen: vorhanden, gültig, nicht abgelaufen
    • Scope je Operation, wie im Vertrag unter security festgelegt
    • Anfrage gegen den Vertrag prüfen: Typen, Pflichtfelder, Grenzen wie maximum und maxLength
    • Rate Limiting und Quoten je Aufrufer
    • Größenlimits: Body, URL, Header, Antwortzeit
    • Nur veröffentlichte Versionen erreichbar machen
    • TLS, CORS, Sicherheits-Header, einheitliche Fehler
    →

    Service prüft fein – mit Fachwissen

    • Gehört dieses Objekt dem Aufrufer?
    • Welche Felder darf er lesen, welche schreiben?
    • Fachliche Regeln: Zustände, Mengen, Vorgänge
    • Grenzen selbst einhalten – auch für Aufrufe ohne Gateway
    • Fehler ohne Interna melden (Problem Details)
    • Eigene Abrufe nach außen nur zu erlaubten Zielen

    Warum das Gateway nicht reicht
    

    Das Gateway kennt Adressen, Methoden, Tokens und den Vertrag – aber keine
Fachlichkeit. Es weiß, dass Tom Mayer reader_access hat. Es weiß nicht, dass
der Kunde 9b2e4c1a-… jemand anderes ist. Die häufigsten Risiken der
OWASP-Liste entstehen genau in dieser Lücke.
    

    Und: Nicht jeder Aufruf kommt über das Gateway. Ein anderer Service im selben
Netz ruft den Account Service direkt. Ein Service, der sich blind darauf verlässt,
dass „vorne schon geprüft wurde“, ist von innen offen. Deshalb prüft der Service
selbst noch einmal, wer fragt – und entscheidet über seine Objekte selbst.
    

    Faustregel: Das Gateway prüft, ob jemand diese Tür benutzen darf. Der Service
prüft, ob er in dieses Zimmer darf.
    

    Robustheit: keine Antwort ohne Grenze
    

    Die meisten Angriffe auf APIs sind kein Einbruch, sondern Überlastung – oft
nicht einmal böswillig. Jede Stelle, an der ein Aufrufer die Menge bestimmt,
braucht eine Obergrenze. Steht sie im Vertrag, setzt das Gateway sie durch.

    API1 · Broken Object Level Authorization Service
    

    

    
Worum geht’s?

    Der Aufrufer ändert die Kennung in der Adresse – und bekommt ein Objekt, das ihm
nicht gehört. Das Token ist gültig, der Scope passt; nur dieses eine Objekt
darf er nicht. Das häufigste API-Risiko überhaupt.
    

    GET /customers/4712
Authorization: Bearer …   (Tom Mayer, Kunde 4711)

HTTP/1.1 200 OK
{ "id": 4712, "name": "Eva Schulz", … }

    

    Wer wehrt ab: nur der Service. Dem Gateway fehlt das Wissen, wem welcher
Kunde gehört.
    

    

    
Do’s

      

    • Bei jedem Zugriff prüfen, ob das Objekt zum Aufrufer gehört – auch bei
Unterressourcen wie /customers/{id}/address.
      • 

    • Kennungen nicht erratbar vergeben (format: uuid) – das erschwert das Raten,
ersetzt die Prüfung aber nicht.
      • 

    • Fremde Objekte mit 404 beantworten, wenn schon ihre Existenz schützenswert ist.
      • 

    

    GET /customers/9b2e4c1a-0d3f-4c55-8a1e-2f5b6c7d77f0
Authorization: Bearer …   (Token von Tom Mayer)

HTTP/1.1 404 Not Found

    

    

    
Don’ts

      

    • „Token gültig“ als „darf alles lesen“ behandeln.
      • 

    • Fortlaufende Kennungen, die man einfach hochzählen kann.
      • 

    • Sich darauf verlassen, dass die Oberfläche nur eigene Kennungen anbietet.
      • 

    

    POST /customers

HTTP/1.1 201 Created
Location: /customers/4712
  → der nächste Kunde ist 4713, der vorige 4711

    

    

    

    

    

    API2 · Broken Authentication Gateway
    

    

    
Worum geht’s?

    Die Prüfung, wer fragt, ist lückenhaft: Abgelaufene Tokens werden angenommen,
Signaturen nicht geprüft, Passwörter lassen sich unbegrenzt durchprobieren,
Tokens stehen in der URL.
    

    GET /customers
Authorization: Bearer eyJhbGciOiJub25lIn0.eyJzdWIiOiJhZG1pbiJ9.
  (selbst gebautes Token: "alg": "none", keine Signatur)

HTTP/1.1 200 OK
{ "items": [ … alle Kunden … ] }

    

    Wer wehrt ab: das Gateway zusammen mit dem Identity Provider – an
einer Stelle, nicht in jedem Service neu erfunden.
    

    

    
Do’s

      

    • Das Token steht im Header Authorization, nie in der Adresse.
      • 

    • Das Gateway prüft Signatur, Ablauf und Aussteller zentral.
      • 

    • Bei Fehlern 401 mit WWW-Authenticate – der Aufrufer erfährt, was fehlt.
      • 

    • Anmeldeversuche begrenzen.
      • 

    

    GET /customers
Authorization: Bearer eyJhbGciOi…

HTTP/1.1 401 Unauthorized
WWW-Authenticate: Bearer error="invalid_token",
  error_description="The access token expired"

    

    

    
Don’ts

      

    • Zugangsdaten oder Tokens in der URL – sie landen in jedem Log, jedem
Browserverlauf, jedem Proxy.
      • 

    • Abgelaufene Tokens „kulanterweise“ annehmen.
      • 

    • Jeder Service baut seine eigene Anmeldung.
      • 

    

    GET /customers?api_key=sk_live_51H8x…&user=admin

    

    

    

    

    

    API3 · Broken Object Property Level Authorization Service Gateway
    

    

    
Worum geht’s?

    Nicht das Objekt, sondern einzelne Felder sind das Problem. Beim Schreiben
setzt der Aufrufer Felder, die er nicht setzen darf (Mass Assignment); beim
Lesen bekommt er Felder, die er nicht sehen soll (Excessive Data Exposure).
    

    GET /customers/3fa85f64-…
Authorization: Bearer …   (Tom Mayer)

HTTP/1.1 200 OK
{ "id": "3fa85f64-…", "name": "Tom Mayer",
  "passwordHash": "$2a$10$N9qo8uLO…",
  "creditScore": 312 }

    

    Wer wehrt ab: der Service. Das Gateway fängt es ab, wenn der Vertrag
unbekannte Felder verbietet – dann weist es die Anfrage schon bei der Prüfung
gegen den Vertrag ab.
    

    

    
Do’s

      

    • Felder, die der Server vergibt, sind readOnly.
      • 

    • Zum Schreiben ein eigenes Schema, das unbekannte Felder verbietet.
      • 

    • Antworten liefern ein ausdrückliches Schema, nicht „die ganze Entität“.
      • 

    • Unterschiedlich geschützte Felder werden eine eigene Ressource – Bezahldaten
unter /customers/{id}/payments.
      • 

    

    CustomerPatch:
  type: object
  additionalProperties: false
  properties:
    name:      { type: string, maxLength: 100 }
    birthdate: { type: string, format: date }

    

    

    
Don’ts

      

    • Den Body ungeprüft auf das gespeicherte Objekt übertragen.
      • 

    • Alle Felder ausliefern und das Ausblenden der Oberfläche überlassen.
      • 

    

    PATCH /customers/3fa85f64-…
{ "name": "Tom Mayer", "state": "aktiv" }

HTTP/1.1 200 OK
{ …, "state": "aktiv" }   ← vorher: gesperrt

    

    

    

    

    

    API4 · Unrestricted Resource Consumption Gateway Service
    

    

    
Worum geht’s?

    Ein Aufrufer bestimmt, wie viel Arbeit der Server leistet – riesige Seiten,
riesige Bodys, unzählige Anfragen, teure Abfragen. Das Ergebnis: Ausfall oder
eine hohe Rechnung.
    

    POST /customers/3fa85f64-…/avatar
Content-Type: image/png
Content-Length: 2147483648   (2 GB)

HTTP/1.1 503 Service Unavailable
  (der Service hat beim Einlesen den Speicher verbraucht)

    

    Wer wehrt ab: das Gateway – es prüft die Grenzen aus dem Vertrag, die
Größe und die Rate. Der Service hält dieselben Grenzen trotzdem ein, für
Aufrufe, die nicht über das Gateway kommen. Siehe Robustheit.
    

    

    
Do’s

      

    • Jede Menge, die der Aufrufer bestimmt, hat im Vertrag eine Obergrenze –
maximum, maxLength, maxItems.
      • 

    • Listen sind paginiert, mit Vorgabe und Obergrenze.
      • 

    • Rate Limits mit 429 und Retry-After.
      • 

    

    - name: limit
  in: query
  schema:
    type: integer
    minimum: 1
    maximum: 200
    default: 50

    

    

    
Don’ts

      

    • Die Menge dem Aufrufer überlassen.
      • 

    • Ohne Parameter „alles“ liefern.
      • 

    • Nur am Eingang begrenzen und zwischen den Services nicht.
      • 

    

    GET /customers?limit=1000000

HTTP/1.1 200 OK   (nach 94 Sekunden)

    

    

    

    

    

    API5 · Broken Function Level Authorization Gateway Service
    

    

    
Worum geht’s?

    Nicht das Objekt, sondern die Funktion ist verboten: Ein
Kundenservice-Konto sperrt Kunden, ein Lesekonto löscht. Oft, weil
Admin-Funktionen nur in der Oberfläche versteckt, an der API aber offen sind.
    

    DELETE /customers/3fa85f64-…
Authorization: Bearer …   (reader_access – darf nur lesen)

HTTP/1.1 204 No Content

    

    Wer wehrt ab: das Gateway, wenn der Vertrag je Operation sagt, welcher
Scope nötig ist. Was feiner ist als ein Scope – Rollen innerhalb eines
Mandanten –, prüft der Service.
    

    

    
Do’s

      

    • An jeder Operation steht im Vertrag, welchen Scope sie verlangt.
      • 

    • Was einen eigenen Schutzbedarf hat, bekommt eine eigene Adresse – dann kann
das Gateway daran prüfen.
      • 

    • 403: Mit diesem Token hilft kein zweiter Versuch.
      • 

    

    /customers/{id}/flags/lock:
  put:
    security:
      - openId: [lock_access]
    responses:
      '403': { $ref: '#/components/responses/Forbidden' }

    

    

    
Don’ts

      

    • Admin-Funktionen nur in der Oberfläche verstecken.
      • 

    • Ein Scope für alles, was schreibt.
      • 

    • Die Sperre als Feld im normalen PATCH.
      • 

    

    PATCH /customers/3fa85f64-…
Authorization: Bearer …   (writer_access)
{ "locked": true }

HTTP/1.1 200 OK

    

    

    

    

    

    API6 · Unrestricted Access to Sensitive Business Flows Service Gateway
    

    

    
Worum geht’s?

    Jede einzelne Anfrage ist korrekt – das Problem ist die Absicht dahinter.
Ein Beispiel: Der Shop schenkt jedem neuen Konto einen Gutschein über 10 €. Ein
Skript legt alle 4 Sekunden ein Konto an, zehn Stunden lang. Das sind 10.000
gültige Anfragen, alle unter dem Rate Limit – und 100.000 € Gutscheine.
    

    POST /customers
{ "name": "Kim Neu 0001", … }

HTTP/1.1 201 Created
{ "id": "…", "voucher": "WELCOME-10-7Q2X" }
  (Anfrage 1 von 10.000 – alle 4 Sekunden die nächste)

    

    Wer wehrt ab: der Service mit fachlichen Regeln. Das Gateway hilft mit
Quoten und Bot-Erkennung, weiß aber nichts von Gutscheinen.
    

    

    
Do’s

      

    • Mit der Fachseite die Abläufe benennen, die automatisiert Geld oder Vertrauen
kosten – Gutscheine, Reservierungen, Bewertungen.
      • 

    • Diese Abläufe fachlich begrenzen – etwa ein Gutschein je Zahlungsmittel.
      • 

    • Quoten und Bot-Erkennung am Gateway als Ergänzung.
      • 

    

    POST /customers
{ "name": "Kim Neu", … }

HTTP/1.1 409 Conflict
{ "title": "Für diese Zahlungsart besteht
   bereits ein Konto", "status": 409 }

    

    

    
Don’ts

      

    • Sich auf das Rate Limit verlassen.
      • 

    • Das Thema der Technik überlassen – es ist eine fachliche Frage.
      • 

    

    POST /customers        → 201 Created
POST /customers        → 201 Created
…  (10.000-mal, je 4 Sekunden Abstand)

    

    

    

    

    

    API7 · Server Side Request Forgery Service
    

    

    
Worum geht’s?

    Die API ruft selbst eine Adresse ab, die der Aufrufer angibt – etwa ein
Profilbild per URL. Dieser Abruf geschieht von innen: Der Server erreicht,
was von außen gesperrt ist – interne Verwaltungsdienste oder die Metadaten der
Cloud mit ihren Zugangsschlüsseln. Der Angreifer lässt den Server für sich
hineinschauen.
    

    POST /customers/3fa85f64-…/avatar
{ "imageUrl": "http://169.254.169.254/latest/meta-data/iam/security-credentials/shop" }

HTTP/1.1 201 Created

GET /customers/3fa85f64-…/avatar

HTTP/1.1 200 OK
{ "AccessKeyId": "ASIA…", "SecretAccessKey": "wJalr…" }

    

    Wer wehrt ab: der Service. Für das Gateway ist die URL nur Text im Body.
Es kann ihre Form prüfen (nur https), aber nicht, wohin sie führt: Ein harmlos
aussehender Name kann auf eine interne Adresse zeigen oder dorthin umleiten.
Das merkt erst, wer den Abruf macht.
    

    

    
Do’s

      

    • Hochladen statt verlinken lassen – dann ruft der Server gar nichts ab.
      • 

    • Muss er abrufen: nur erlaubte Ziele, keine internen Adressen, keinen
Umleitungen folgen, Größe und Zeit begrenzen.
      • 

    

    POST /customers/3fa85f64-…/avatar
Content-Type: image/png
(Bilddaten, höchstens 2 MB)

HTTP/1.1 201 Created

    

    

    
Don’ts

      

    • Jede URL laden, die im Body steht.
      • 

    • Nur die Form der URL prüfen und dann blind abrufen.
      • 

    

    POST /customers/3fa85f64-…/avatar
{ "imageUrl": "https://bild.example.net/tom.png" }
  (der Name zeigt auf 169.254.169.254)

HTTP/1.1 201 Created

    

    

    

    

    

    API8 · Security Misconfiguration Gateway Service
    

    

    
Worum geht’s?

    Nicht der Entwurf ist falsch, sondern der Betrieb: Stacktraces in
Fehlermeldungen, CORS für *, unverschlüsseltes HTTP, Debug-Endpunkte in
Produktion, fehlende Sicherheits-Header.
    

    GET /customers
Origin: https://boese-seite.example
Cookie: session=…

HTTP/1.1 200 OK
Access-Control-Allow-Origin: https://boese-seite.example
Access-Control-Allow-Credentials: true
  (die API spiegelt jede Origin zurück)

    

    Wer wehrt ab: das Gateway für alles, was einheitlich sein soll – TLS,
CORS, Header –, der Service für seine Fehlermeldungen.
    

    

    
Do’s

      

    • TLS überall, auch intern.
      • 

    • CORS nur für bekannte Origins.
      • 

    • Fehler im vereinbarten Format (Problem Details), verständlich und ohne
Innenleben.
      • 

    

    HTTP/1.1 400 Bad Request
Content-Type: application/problem+json

{ "title": "Ungültiger Cursor",
  "detail": "Bitte die Liste von vorn laden.",
  "status": 400 }

    

    

    
Don’ts

      

    • Stacktraces und SQL in der Antwort.
      • 

    • Access-Control-Allow-Origin: * für eine API mit Anmeldung.
      • 

    • Debug-Endpunkte in Produktion.
      • 

    

    HTTP/1.1 500 Internal Server Error

{ "error": "SQLSyntaxErrorException at
  CustomerRepository.findAfter(…):
  SELECT * FROM t_customer WHERE …" }

    

    

    

    

    

    API9 · Improper Inventory Management Gateway
    

    

    
Worum geht’s?

    Niemand weiß genau, welche APIs und Versionen erreichbar sind. Die alte v0,
die Testumgebung mit echten Daten, der vergessene Endpunkt – sie laufen weiter,
ohne die Prüfungen der neuen.
    

    GET https://api.test.example.com/v1/customers
  (Testumgebung, ohne Token)

HTTP/1.1 200 OK
{ "items": [ … echte Kundendaten, Abzug von gestern … ] }

    

    Wer wehrt ab: ein Inventar – jede API hat einen Vertrag, jede Version
einen Abschalttermin – und das Gateway, das nur erreichbar macht, was dort
verzeichnet ist.
    

    

    
Do’s

      

    • Jede API und jede Version mit Vertrag und Abschalttermin verzeichnen.
      • 

    • Die Abschaltung ankündigen und danach eindeutig antworten.
      • 

    

    GET /v1/customers

HTTP/1.1 200 OK
Deprecation: @1767225600
Sunset: Wed, 30 Jun 2027 23:59:59 GMT

    

    

    
Don’ts

      

    • Die alte Version „sicherheitshalber“ weiterlaufen lassen.
      • 

    • Testumgebungen mit echten Daten offen erreichbar.
      • 

    

    GET /v0/customers?limit=1000000
(kein Token nötig – v0 kannte noch keins)

HTTP/1.1 200 OK

    

    

    

    

    

    API10 · Unsafe Consumption of APIs Service
    

    

    
Worum geht’s?

    Die eigene API ist selbst Aufrufer – etwa einer Adressprüfung oder eines
Zahlungsdienstes. Deren Antworten werden ungeprüft übernommen, weil der
Partner ja „vertrauenswürdig“ ist. Ist der Partner kompromittiert oder fehlerhaft,
landet sein Inhalt ungefiltert in der eigenen Datenbank.
    

    GET https://adressen.partner.example/check?zip=50667
  (der Account Service fragt den Partner)

HTTP/1.1 200 OK
{ "zip": "50667",
  "city": "Köln'); DROP TABLE address;--" }
  → ungeprüft in die eigene Datenbank übernommen

    

    Wer wehrt ab: der Service, der den Partner aufruft. Kein Gateway steht
dazwischen.
    

    

    
Do’s

      

    • Die Antwort des Partners gegen dessen Vertrag prüfen – wie jede Eingabe.
      • 

    • Zeitlimit und Größenlimit setzen, nur https.
      • 

    

    GET https://adressen.partner.example/check?zip=50667

HTTP/1.1 200 OK
{ "zip": "50667", "city": "Köln" }

    

    

    
Don’ts

      

    • Antworten ungeprüft speichern oder weiterreichen.
      • 

    • Umleitungen des Partners blind folgen.
      • 

    

    HTTP/1.1 200 OK
{ "zip": "<script>…</script>",
  "city": "… (48 MB)" }
