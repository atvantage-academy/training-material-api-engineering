    Kursbeschreibung

    Zielgruppe

    Alle, die an einer HTTP-Schnittstelle mitarbeiten – Softwareentwickler:innen (Backend und Frontend), Architekt:innen, Tester:innen und QA sowie Product Owner und fachliche Rollen, die Schnittstellen abstimmen oder abnehmen.

    Vorkenntnisse: Erfahrung mit Software-Projekten und ein Grundverständnis von Web-Anwendungen genügen. Programmierkenntnisse sind nicht erforderlich – im Kurs wird nichts implementiert, sondern entworfen. Wer schon einmal eine API aufgerufen oder getestet hat, findet sich schneller zurecht; wer es nicht hat, holt es am ersten Vormittag auf.

    Der Kurs ist bewusst nicht in Grundlagen- und Vertiefungsteil getrennt. Jedes Thema beginnt bei der Anschauung und geht dann in die Tiefe, die für eine belastbare Entscheidung nötig ist – so kommen gemischte Gruppen gemeinsam durch.

    Überblick

    Eine API ist das Aushängeschild eines Systems. Sie ist wie die Speisekarte eines Restaurants: Wer sie liest, muss ohne Rückfrage erkennen, was es gibt, was es kostet und was passiert, wenn er bestellt. Schlecht entworfene APIs erkennt man daran, dass jede Nutzung eine Rückfrage auslöst – und daran, dass sich Fehler niemals nur im eigenen System auswirken, sondern bei allen, die davon abhängen.

    REST ist kein Framework und keine Bibliothek, sondern eine Haltung: HTTP so zu nutzen, wie es beim Entwurf gedacht war. Genau das macht den Unterschied zwischen einer Schnittstelle, die ein Netzwerk aus Proxies, Caches und Gateways einfach mitträgt, und einer, die überall Sonderbehandlung braucht.

    In zwei Tagen bauen wir dieses Verständnis von unten auf: erst die Mechanik von HTTP, dann die Entwurfsregeln, dann ein eigener Entwurf einer Kundenverwaltung, den wir am zweiten Tag gemeinsam auseinandernehmen und schließlich als OpenAPI formulieren. Am Ende steht nicht Wissen über REST, sondern die Fähigkeit, eine API zu entwerfen und einen fremden Entwurf zu beurteilen.

    Lernziele

    Die Lernenden…

    • benennen die Bestandteile einer HTTP-Nachricht und lesen den Verkehr einer Anwendung mit Browser-Entwicklerwerkzeugen und einem HTTP-Client mit.
    • bilden CRUD-Operationen auf HTTP-Methoden ab und begründen je Ressourcenart, welche Methode zulässig, sinnvoll oder verboten ist.
    • unterscheiden idempotente von nicht-idempotenten Operationen und entwerfen für einen fachlichen Auftrag eine idempotente Variante.
    • entwerfen zu einer fachlichen Anforderung ein Ressourcenmodell und begründen, wann etwas Subressource, eingebettetes Feld oder eigene Hauptressource wird.
    • übersetzen einen API-Entwurf in ein OpenAPI-Dokument und beurteilen ein fremdes OpenAPI-Dokument auf Vollständigkeit und Sauberkeit.
    • begründen die Wahl zwischen Contract First und Code First anhand der Lage, in der eine API entsteht.

    Agenda (2 Tage)

    Warum es überhaupt Schnittstellen gibt

    • Woran man merkt, dass ein System zu groß geworden ist – und wie der Schnitt entlang der Fachlichkeit aussieht (Microservices, Domain-Driven Design)
    • Was man sich mit jeder zusätzlichen Schnittstelle einhandelt und was man dafür bekommt
    • Warum ausgerechnet HTTP das Protokoll der Wahl wurde – und was „REST“ damit zu tun hat (Fielding 2000)

    Was auf der Leitung passiert

    • Wie eine Anfrage und ihre Antwort aufgebaut sind – und welcher Teil wofür da ist
    • Warum ein Server sich nichts merken darf, und was das für die eigene Anwendung bedeutet (Zustandslosigkeit)
    • Wie man dem eigenen System beim Sprechen zusieht, ohne Code zu schreiben (Entwicklerwerkzeuge, curl, HTTP-Clients)
    • Woran man erkennt, welcher Header gerade das Problem verursacht

    Adressen, Verben, Antworten

    • Wie man eine Sache so benennt, dass die Adresse ohne Dokumentation verständlich ist
    • Welche Operation auf welche HTTP-Methode gehört – und woran man merkt, dass eine Kombination gar keinen Sinn ergibt
    • Wann eine Antwort einen Körper braucht und wann nicht
    • Wie Client und Server sich auf ein Format einigen (Content Negotiation)
    • Welcher Statuscode etwas aussagt und welcher nur höflich ist
    • Was passiert, wenn dieselbe Anfrage zweimal ankommt – und warum das kein Randfall ist (Idempotenz)
    • Wie man eine Liste leert, ohne sie zu löschen

    Eine API entwerfen

    • Wie man aus einer fachlichen Beschreibung Ressourcen herausliest
    • Wann ein Detail ein eigenes Ding wird und wann es in das übergeordnete gehört
    • Woran man erkennt, dass eine Subressource eigentlich eine Hauptressource ist
    • Wie man eine Operation modelliert, die sich nicht als CRUD lesen lässt
    • Wie ein fremder Entwurf beurteilt wird, ohne über Geschmack zu streiten

    Den Vertrag aufschreiben

    • Warum eine Schnittstellenbeschreibung mehr ist als Dokumentation
    • Wie ein OpenAPI-Dokument aufgebaut ist und wo man beim Schreiben anfängt
    • Wie man Wiederholung vermeidet, ohne unlesbar zu werden (Komponenten, $ref)
    • Ob die Beschreibung vor oder nach dem Code entsteht – und was jeweils davon abhängt (Contract First ↔ Code First)
    • Welche Aufgaben gar nicht im eigenen Code landen, weil sie davor erledigt werden (API Gateway, CORS)

    Was danach kommt (nach Zeit und Interesse)

    • Wie man eine Schnittstelle ändert, ohne die Nutzer zu brechen (Versionierung, Breaking Changes)
    • Was man tut, wenn die Antwort eine Million Datensätze enthielte (Paginierung)
    • Wie man Fehler so meldet, dass der Aufrufer damit etwas anfangen kann (Problem Details, RFC 9457)
    • Wann eine andere Art von Schnittstelle die bessere Wahl wäre (SOAP, GraphQL, gRPC)
    • Was es bedeutet, wenn die Antwort dem Client sagt, was er als Nächstes tun kann (Hypermedia, HAL)
