Contract First oder Code First?

Contract First oder Code First?

Zwei Wege, zu einer beschriebenen Schnittstelle zu kommen. Beide haben gute Argumente – und ein klares Einsatzgebiet. Diese Seite stellt sie so gegenüber, dass Du damit im eigenen Unternehmen argumentieren kannst.

Code First

Die Implementierung entsteht zuerst – oder liegt als Altbestand schon vor. Die API-Beschreibung wird per Annotationen aus dem Code erzeugt, aus ihr optional Client-Code.

Contract First

Die API wird von Hand entworfen und aufgeschrieben. Aus der Beschreibung lässt sich bei Bedarf Gerüstcode für Server und Client erzeugen – muss aber nicht.

Was für Code First spricht – und was dagegen einzuwenden ist

Diese Argumente sind nicht aus der Luft gegriffen. Sie sind der Grund, warum Code First so verbreitet ist – und wer sie übergeht, überzeugt niemanden.

„Die Lernkurve ist niedriger.“

Als Entwickler kenne ich meine Sprache. Eine API in einem gewohnten Format zu formulieren fällt mir leichter, als ein neues Beschreibungsformat zu lernen. Notfalls lerne ich ein paar Annotationen dazu. Das Beschreibungsformat meide ich, weil es kompliziert wirkt – und weil mir kein Compiler sagt, ob es stimmt.

Einwand: Beides lässt sich auflösen. Editoren und IDEs bieten für das Beschreibungsformat Vervollständigung, Hervorhebung und Umbenennen; statt eines Compilers gibt es Validatoren, die in jeder Pipeline laufen. Der Aufwand ist einmalig, das Ergebnis dauerhaft.

„Die API passt garantiert zum Code.“

Was ich herausgebe, entspricht exakt der Implementierung. Ändert sich der Code, ändert sich die Beschreibung automatisch mit. Es kann keine Abweichung geben.

Einwand: Genau darin liegt die Gefahr. Wird die API von anderen Teams genutzt, ist die automatische Änderung kein Vorteil, sondern ein unbemerkter Vertragsbruch. Was heute Komfort ist, ist morgen ein Produktionsvorfall bei jemand anderem.

„Für Prototypen bin ich schneller.“

Wenn ich noch wenig Erfahrung mit API-Design habe, erkenne ich im Code schneller, was möglich ist und was nicht – und welche Informationen ich überhaupt brauche, um die Fachlichkeit abzubilden.

Einwand: Stimmt – für einen Prototyp. Der Haken ist nur, dass Prototypen selten sterben. Wer so anfängt, sollte den Zeitpunkt festlegen, an dem die Beschreibung die Führung übernimmt.

Was für Contract First spricht

Die API ist ein Produkt

Eine API hat Anforderungen, ein verantwortliches Team, einen eigenen Entwicklungszyklus, eine eigene Versionierung und eigene Releases. Ihre Implementierung kann aus einem oder mehreren Projekten bestehen, jedes mit eigenem Lebenszyklus – daran sollte die API nicht eng gekoppelt sein.

Dazu kommt: Wie eine Benutzeroberfläche ist die API das Aushängeschild des Teams nach innen und des Herstellers nach außen. Ob man dieses Aushängeschild von einem Generator erzeugen lassen möchte, darf man kritisch sehen.

Es gibt zwei APIs, nicht eine

Die öffentliche API am Gateway – das, was Frontends und andere Dienste sehen, samt Gateway-Konfiguration, zusätzlichen Headern und Verweisen auf Operationen. Und die interne API der Implementierung, die das Gateway aufruft; sie kann andere Header tragen und andere Datentypen verwenden, wenn das Gateway übersetzt.

Im einfachsten Fall sind beide gleich. Sobald aber eine öffentliche API von mehreren Implementierungen bedient wird – etwa weil eine Funktion besser als eigenständiger Dienst läuft –, lässt sich die öffentliche API gar nicht aus Code erzeugen. Nach außen steht die Fachlichkeit, nach innen bleibt die Umsetzung frei.

Fallstricke der Generierung vermeiden

  • Hinter scheinbar kleinen Codeänderungen entstehen schnell und unbewusst Breaking Changes – nicht nur für die Nutzer, sondern auch in der Infrastruktur. Das Gateway passt sich dem Code an; damit entfällt die zweistufige, unabhängige Prüfung, die das BSI empfiehlt. Ein umbenannter Methodenname ändert die Kennung der Operation, auf die das Gateway schaltet.
  • Fehler im Generator wirken sich auf die API aus – und Unschönheiten darin sind öffentlich sichtbar.
  • Auch ohne Fehler muss die erzeugte Beschreibung nach Clean-Code-Gesichtspunkten geprüft werden, etwa auf einmalig definierte und wiederverwendete Parameter.
  • Bei mangelhafter Konfiguration werden interne Schnittstellen öffentlich – der Klassiker sind Betriebs- und Diagnose-Endpunkte, die standardmäßig in der Beschreibung landen, am Gateway aber nichts zu suchen haben.

Kein unnötiger Code

Um eine saubere Beschreibung zu erhalten, muss man den Code verbiegen. So entsteht Code, der nur für die API da ist. Manches muss überhaupt nicht implementiert werden – CORS und Authentifizierung erledigt das Gateway davor –, und die Gateway-Konfiguration lässt sich im Code gar nicht ausdrücken.

Nebenbei leidet die Lesbarkeit: Der Code beschreibt dann auch noch sich selbst. Von Trennung der Zuständigkeiten kann keine Rede mehr sein.

Technologieneutralität

HTTP-basierte Schnittstellen sind technologieneutral; aus einer Beschreibung lässt sich Code für unterschiedliche Sprachen und Rahmenwerke erzeugen. Code First gefährdet genau das:

  • Framework-eigene Datentypen machen die Beschreibung technologiespezifisch.
  • Wird keine optimale Beschreibung erzeugt, wird auch der daraus erzeugte Client-Code suboptimal.
  • Sie verrät unnötige Informationen an potenzielle Angreifer.

Besseres Verständnis für fremde APIs

Wer das Beschreibungsformat selbst schreibt, erwirbt ein tieferes Verständnis für API-Design im Allgemeinen – und versteht damit auch fremde APIs besser. Das ist der Nutzen, der am längsten bleibt.

Die API folgt dem Anwendungsfall

Im Idealfall ergibt sich die API aus den fachlichen Anforderungen – nicht aus dem Datenbankschema und den Eigenheiten der Implementierung (typisch für Code First) und nicht aus den Dialogen der Oberfläche.

Am leichtesten gelingt das, wenn beim Entwurf gar kein Code im Spiel ist, sondern ein technologieunabhängiges Format – das hält den Blick auf dem, was die API leisten soll.

Das Fazit in drei Sätzen

Contract First gehört zum Standardvorgehen. Nur wenn wir die Beschreibung selbst schreiben, haben wir die volle Kontrolle und das volle Bewusstsein über eine sauber dokumentierte Schnittstelle.

Code First eignet sich für Schnittstellen zwischen Systemen, die team-intern entwickelt, betrieben und genutzt werden – und team-intern bleiben. Diese APIs brauchen wenig Dokumentation und verlangen auch keine strikte Einhaltung von Clean-Code- oder REST-Prinzipien.

Sobald die Wahrscheinlichkeit besteht, dass ein anderes Team auf die API zugreift – und sei es nur die Qualitätssicherung –, ist Code First nicht mehr anwendbar.
